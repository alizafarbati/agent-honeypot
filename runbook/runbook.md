## 1. OPERATIONAL DOCTRINE (non-negotiable)

1.1 ZERO WEAPONIZATION RULE
Every lure, capture mechanism, and interaction design remains defensive. The framework is built to observe, fingerprint, and stall unauthorized AI agents operating against this infrastructure. It does not provide capabilities for unauthorized offensive operations, and all anti-weaponization controls (Zone B zero-egress, synthetic-only responses, audit-only counter-actions) are enforced by design, not by policy alone.

1.2 ZERO-TRUST BETWEEN PLANES
Zone A (Edge), Zone B (Deception Surface), Zone C (Capture/Analysis), Zone D (Evolution/Control) do not share secrets, do not share compute contexts, and communicate exclusively over the signed message bus (NATS JetStream, mTLS, JWT claims). Compromise of any single zone does not grant access to others.

1.3 DEFENSE-IN-DEPTH FOR DECEPTION
The deception surface (Zone B) is the most exposed layer by design. Every internal component carries independent defensive controls: CAITLYN Tier-0 injection detection on all LLM inputs; eBPF syscall auditing; ephemeral storage; no persistent credentials mounted.

1.4 AUDIT-NON-REPUDIABLE
Every lure promotion, counter-action escalation, session replay, and SIEM emission is logged to an immutable audit store (separate from operational database) with cryptographic chain verification (SHA-256 linked list, not blockchain — operational simplicity, audit integrity).

## 2. INCIDENT RESPONSE MATRIX (defensive — not offensive)

|---|---|---|---|---|
| TIER 1 | Honey credential CANARY triggered on real endpoint (deployment failure — real service contacted) | Freeze new lure deployment; alert on-call; capture full session replay | Verify no real service compromise; rotate canary; audit Zone B egress | < 5 min |
| TIER 2 | Session fingerprint indicates new high-capability agent family (unknown harness + autonomous posture + high injection susceptibility) | Shadow-deploy enhanced lure family; begin System-II synthesis; freeze promotion pipeline | Review session replay; approve enhanced bait; verify no meta-attack | < 30 min |
| TIER 3 | Multiple sessions with same actor-cluster fingerprint + credential-use + persistent-goal attempts (active adversarial campaign) | Deploy campaign-level lure variant; elevate counter-action gate from observe-only to stall mode per policy | Confirm campaign scope; initiate STIX/TAXII feed update; contact external ISAC if required | < 1 hr |
| TIER 4 | Evidence of meta-attack (interrogator/analyzer targeted; lure mutation attempt; internal framework fingerprinting) | Freeze System-II synthesis; rollback to previous verified defense library; audit all planner inputs since last checkpoint | Execute full incident response; review audit chain; assess framework integrity; update CAITLYN antibody library | < 4 hr |

## 3. SECURITY CONTROLS (mapped to defensive controls, not theoretical)

3.1 ZONE ISOLATION CONTROLS (enforced in code + infrastructure)
- Kubernetes NetworkPolicy: deny-all-default, explicit allow lists only
- Calico eBPF: deny-all-egress from Zone B pods except to specific Zone C NATS endpoints (IP + port + JWT claim allowed only)
- Pod Security Standards: Zone B = restricted (no privileged, no hostPath, no serviceAccount cluster-admin, readOnlyRootFilesystem: true)
- Secrets: Vault dynamic secrets only; Zone B mounts zero Kubernetes secrets; session tokens expire at session termination

3.2 ANTI-FINGERPRINTING CONTROLS (operational discipline)
- Every lure family deploys with at least 3 active schema variants (name rotation + field-order variation + description rephrasing) — attacker fingerprinting requires matching across all variants, increasing adversary cost
- Fidelity budget enforced in CI: any lure release must pass the anti-fingerprint red-team battery (see evaluation harness) before promotion from shadow to live
- Per-tenant lure isolation: multi-tenant framework uses separate ClickHouse partitions + separate Vault namespaces; lure libraries never cross-tenant boundaries

3.3 ANTI-WEAPONIZATION CONTROLS (defensive engineering mandate)
- Synthetic-only responses: all Zone B responses are generated by the Response Synthesizer using LLM-driven synthetic corpora; no real database/API/credential endpoint is contacted by the deception framework
- Session-boundary enforcement: interactive modules (`ssh_exec`, `cli_shell`) enforce max session time (30 min sticky), max paginated pages, no recursive execution, no external callbacks — these are stall mechanisms, not escalation mechanisms
- Audit chain integrity: every lure promotion (shadow → live), every counter-action policy change, and every session replay is appended to the immutable audit log with previous hash reference (non-blockchain audit chain for operational efficiency and forensic reliability)

## 4. OPERATIONAL PROCEDURES (runbook reference only — full automated execution is framework default)

4.1 DAILY HEALTH CHECK (automated via daemon `/v1/health` endpoint)
- Verify Zone B VM health: all sandbox instances responsive
- Verify Zone C message bus: event throughput within baseline ±20%
- Verify Zone D synthesis pipeline: no stuck shadow deployments (no lure in shadow > 14 days without promotion/rejection decision)
- Verify canary webhook endpoints: all registered, all responsive
- Verify audit chain: last entry hash matches previous (integrity check)

4.2 WEEKLY LURE REVIEW (human-in-the-loop, framework-enforced gate)
- Review all shadow-deployed lures: effectiveness rate (capture rate vs false engagement rate)
- Promote/demote/retire per A/B bandit statistics; retire any lure with decaying capture rate (>20% drop over 2-week window indicates adversary immunization)
- Verify all active lure families have current anti-fingerprint red-team pass results

4.3 MONTHLY AUDIT REVIEW
- Full replay of highest-tier sessions (TIER 3-4) for intelligence extraction verification
- Cross-actor clustering review: new campaigns, new model-family signatures, new harness identities
- Update STIX feed; verify SIEM integration health; review compliance retention settings

## 5. COMPLIANCE AND GOVERNANCE

5.1 DATA CLASSIFICATION
- Session data (raw transcripts, fingerprints, extracted payloads) = "Intelligence — Restricted — Defensive"
- Actor clustering results, TTP mappings = "Intelligence — Internal — Operational"
- Audit logs = "Audit — Immutable — Forensic"
- All data encrypted at rest (LUKS / database-level encryption); keys in Vault; rotation every 90 days

5.2 ACCESS CONTROL (role-based, enforced at framework API layer)
- `agent-honeypot-operator`: access to session replay, fingerprint review, lure rotation approval; no STIX emission without co-signature
- `agent-honeypot-analyst`: full replay, correlation engine, TTP mapping; no lure promotion
- `agent-honeypot-engineer`: full framework access including System-II synthesis parameters; audit-required for all counter-action policy changes
- `agent-honeypot-auditor`: audit-log read-only; no framework mutation capabilities

5.3 RETENTION AND EXPIRY
- Raw transcripts (Zone C storage): 30 days hot (ClickHouse), 365 days cold (object store); auto-purge after 365 days
- Fingerprint feature data: 90 days; aggregated actor clusters retained 2 years for campaign tracking
- Audit logs: 7 years (forensic retention); stored in immutable chain format
- Canary webhook response data: 30 days; used only for confirmation of malicious execution

5.4 ETHICAL ENGINEERING NOTE
This framework is designed and deployed exclusively as defensive deception infrastructure. All counter-measure capabilities (stall, observe, interrogate) are bounded by policy gates, audit requirements, and synthetic-only interaction design. The framework does not provide offensive automation capabilities; every component carries defensive-security engineering controls that enforce its defensive character independently of operational intent.
